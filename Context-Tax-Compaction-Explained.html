The Context Tax, Explained Simply

A plain-language summary of The Context Tax: When to Compact Your Coding Agent by Rogerio Chaves (August 2, 2026), based on 2,451 agent sessions, 287,748 API calls and 873 compactions.

In one sentence: a huge context window feels like a free upgrade, but you pay to re-read all of it on every step while the agent only uses a tiny slice. Compact somewhere around 250k to 450k tokens, start helper agents fresh, and keep some recent history word-for-word when you compact.

1. The basic idea

A coding agent like Claude Code keeps a running memory of the whole conversation: your messages, the files it read, the commands it ran and their output. That memory is the context window, measured in tokens (roughly word-pieces).

Compacting replaces that long history with a short summary, so the agent can start fresh but still know roughly what is going on. The blog asks one question: when should you compact?

2. Why big contexts get expensive fast

This is the point most people miss: every time the agent does anything, it re-reads its entire memory.

Picture a student who, before writing each new sentence of an essay, rereads every page of notes from the start. With 10 pages that is cheap. With 500 pages every sentence is expensive, even though only one sentence is being added.

If an agent sits at 500k tokens and runs 25 commands (tests, lint and so on), you pay for 25 × 500k tokens, not 500k once. In the author's data, running the test suite once cost about 568,000 tokens before any test actually ran.

Caching makes re-reading about 10× cheaper per token, but you still pay on every single step, so it does not fix the underlying problem. Cached reads were 95% of all tokens on the author's worst day.

The "6× per doubling" rule

Each time the context doubles, the total cost of getting there goes up about 6× (a power law with exponent about 2.55).

Context size reachedMedian total tokens spent to get there
100kabout 1.4 million
200kabout 9 million
800kabout 338 million (250× the cost of 100k, for 8× the window)

Very small windows are wasteful too: below about 50k the agent has not gathered enough to produce anything substantial. The most efficient point for tokens read per token written was around 75k. So there is both a floor and a ceiling.

3. The disaster that started it all

The author burned 2.25 billion tokens in one day and kept hitting usage limits. Two forked subagents caused about half of it. A forked subagent is a helper agent that starts with a full copy of the parent's memory instead of a clean slate.

  • A fresh helper starts at about 30k tokens.
  • These two started at 523k and 304k, ran for 8 to 10 hours, and one peaked at nearly 1M tokens.
  • One ran 1,112 shell commands, each re-reading the whole window.

Lesson: give helper agents a fresh start and a short brief instead of a copy of a huge context. Also, how many steps a task takes is close to unpredictable (median 20 calls, but the worst took 1,545), and whatever size you start an agent at gets multiplied by that.

4. Is all that memory actually useful?

Mostly no. An AI judge checked which parts of the memory the agent actually used at each step:

Typical context sizePart actually usedShare
about 39kabout 8kabout 47%
about 645kabout 8.5kabout 2.5%

The memory grew 16× while the useful part stayed about the same size. Most of a giant context is dead weight you keep paying to re-read.

The judges also asked whether a summary would have worked instead of the original text. For 85% of steps it would. The exact original mattered mainly when the agent had to copy something character-for-character, such as the search text of a code edit or a literal connection string. Decisions, constraints and findings survived a summary fine.

5. The catch: compaction makes the agent worse for a while

If big contexts are wasteful, why not compact all the time? Because right after a compaction the agent goes through a post-compaction fog:

  • It re-reads files and re-learns things it used to know (about 28 steps of rediscovery).
  • It makes worse decisions. In the first 5 steps after a compaction, the author corrected the agent 2.4× more often (42% of messages vs. 18% normally).
  • The effect lasts 30 to 100+ steps, even though tool errors stay flat: the commands still work, but the choices behind them get worse.

Compaction today is brutal: a typical one squeezes 575k tokens down to about 4k, so less than 1% survives, and it takes about 2.5 minutes.

Compact too often and you are nearly always in the fog (about 29% of steps at a 220k threshold vs. 9% at 577k). Compact too rarely and you pay a fortune to re-read junk. The goal is the sweet spot in between. When unsure, err on compacting a little late: compacting too early hurts more than compacting too late.

6. The recommendation

Compact somewhere between about 250k and 450k tokens, depending on the kind of work:

Kind of workCompact aroundWhy
Driving a PR to merge200k – 250kBarely needs old details (2% needed the exact text)
Research250k – 300kTasks are self-contained
QA / testing250k – 350kOld results go stale quickly
Building features300k – 450kNeeds exact text for edits
Understanding code300k – 450kKnowledge builds up over time
  • Below about 200k: too much of your time is spent in the fog.
  • Above about 600k: you pay a big premium for no measurable benefit.
  • Near 1M: the author found no justification at all.

7. Two bigger levers than the threshold

  • Better compaction. Keep the last 30k to 60k tokens word-for-word plus a summary of the rest, instead of a tiny 4k summary. In the author's model, a 350k threshold with a 60k preserved tail costs 25% less than a 600k threshold with a plain summary.
  • Where helper agents start. Start subagents fresh (about 30k) instead of forking them from a loaded parent.

8. Honest caveats

  • It is one person's usage on one codebase; exact numbers will differ, but the general patterns (power-law cost, flat useful context, post-compaction spike) probably carry over.
  • The correction-rate finding may be partly inflated, because people often compact when things are already going badly.
  • The cost of a bug that slips through because of compaction (engineer time, customer trust) is not in the data. If that cost is high enough, a larger window might still be worth it.

9. Quick glossary

TermMeaning
TokenA chunk of text, roughly a word-piece. Models are billed per token.
Context windowEverything the model sees on a given request: the whole conversation so far.
CompactionReplacing the conversation with a summary to shrink the window.
CachingReusing already-processed text at a lower price. Cheaper, but still paid every step.
SubagentA helper agent the main agent spawns to do one task.
Forked subagentA subagent that starts with a full copy of the parent's context.
Power lawA curve where cost grows much faster than size (here about 6× per doubling).
