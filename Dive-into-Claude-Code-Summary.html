Dive into Claude Code: The Design Space of Today's and Future AI Agent Systems

Summary of arXiv 2604.14228v3 (Liu, Zhao, Shang, Shen — VILA Lab, MBZUAI), 55 pages. Covers every section except the reference list.

The short version

  1. The core of Claude Code is a simple while loop: call the model, run the tools it asks for, repeat until it answers with text only. Only about 1.6% of the code is "AI decision logic". The other 98.4% is the harness around it: permissions, context management, extensions, subagents and persistence.
  2. The bet is "minimal scaffolding, maximal harness." Claude Code doesn't force the model through planners or state graphs the way LangGraph or Devin do. It gives the model freedom and surrounds it with deterministic infrastructure. The model decides, and the harness enforces.
  3. The context window is the scarce resource (200K, or 1M for the 4.6 series). A lot of the design exists to save it: a 5-layer compaction pipeline, lazy-loaded instructions, deferred tool schemas, and subagents that return only a summary.
  4. Safety is deny-first and layered. There are 7 permission modes and 7 independent safety layers. This exists because users approve 93% of permission prompts, so you can't rely on a human clicking "yes" carefully.
  5. The paper's main criticism: the architecture boosts short-term productivity but has almost nothing that protects long-term developer understanding, skills or codebase coherence.

1. What the paper is and how it was done

  • Method: source-code analysis of Claude Code v2.1.88, taken from the publicly available npm package (about 1,884 files and 512K lines of TypeScript). It's compared with two open-source agents, OpenClaw and Hermes Agent.
  • Evidence tiers. Know these if anyone challenges the paper's claims:
    • Tier A: official Anthropic documentation. It shows intent, not necessarily implementation.
    • Tier B: verified against specific files and functions. This is the strongest tier.
    • Tier C: community analysis or inference. These claims are hedged.
  • Running example: the paper follows one task, "Fix the failing test in auth.test.ts", through every subsystem.

2. Five values and thirteen principles (Section 2)

The five human values behind the design

ValueMeaningKey evidence
Human Decision AuthorityThe human has the final say: observe, approve, interrupt, audit. Authority runs Anthropic → operators → users.93% approval rate led to defined boundaries (sandbox, classifier) instead of more prompts.
Safety, Security, PrivacyProtect the user even when they aren't paying attention.The auto-mode threat model covers overeager behavior, honest mistakes, prompt injection and misalignment.
Reliable ExecutionDo what was meant, stay coherent over long work, and verify.Loop of gather context → act → verify. Agents tend to praise their own work, so generation should be separate from evaluation.
Capability AmplificationMore output per unit of effort.About 27% of Claude Code-assisted tasks would not have been attempted at all.
Contextual AdaptabilityFits your project, and trust grows over time.Auto-approve rate rises from about 20% (under 50 sessions) to over 40% (750 sessions).

The thirteen design principles

  1. Deny-first with human escalation
  2. Graduated trust spectrum
  3. Defense in depth
  4. Externalized programmable policy (hooks and config)
  5. Context as a scarce resource
  6. Append-only durable state
  7. Minimal scaffolding with a maximal harness
  8. Values over rules
  9. Composable extensibility through several mechanisms
  10. Reversibility-weighted risk (lighter checks for read-only or reversible actions)
  11. Transparent file-based memory
  12. Isolated subagents
  13. Graceful recovery

Three alternative design families the paper contrasts with

  • Rule or graph orchestration (LangGraph)
  • Container isolation (SWE-Agent, OpenHands)
  • Git rollback as the safety net (Aider)

The cross-cutting concern: long-term developer capability. It is not a design value in Claude Code, and the paper says so explicitly. For example, developers using AI scored 17% lower on comprehension tests.

3. Architecture overview (Section 3)

Four core design questions and Claude Code's answers

  • Where does reasoning live? In the model. The harness executes. The model can only emit tool_use blocks, so even a compromised model can't override sandboxing or deny rules.
  • How many execution engines? One: queryLoop() in query.ts. The CLI, headless claude -p, Agent SDK and IDE all share it. QueryEngine is only a wrapper for SDK and headless use. This is a common misconception the paper corrects.
  • Default safety posture? Deny-first. Deny rules beat ask rules, ask rules beat allow rules, and anything unrecognized escalates to the user.
  • Binding constraint? The context window.

Seven components: user, interfaces, agent loop, permission system, tools, state and persistence, execution environment.

Five layers:

  • Surface: CLI, SDK, IDE
  • Core: the loop and compaction
  • Safety/action: permissions, hooks, tools, sandbox, subagents
  • State: context, memory, transcripts
  • Backend: shell, MCP, remote execution

4. The agent loop (Section 4)

Each turn

  1. Resolve settings.
  2. Initialize one mutable State object.
  3. Load messages since the last compaction boundary.
  4. Run the 5 context shapers.
  5. Stream the model call.
  6. Dispatch tools.
  7. Pass each request through the permission gate.
  8. Execute and append tool_result.
  9. Stop if the response has no tool calls.

Tool execution

  • StreamingToolExecutor starts running tools while the model is still streaming.
  • Reads run in parallel and writes are serialized.
  • If one Bash command fails, its sibling processes are aborted.

The five shapers, from cheapest to most aggressive

  1. Budget reduction: caps the size of each tool result.
  2. Snip: trims old history.
  3. Microcompact: cache-aware fine-grained compression.
  4. Context collapse: a read-time projection. The model sees a collapsed view, but the full history stays stored.
  5. Auto-compact: a full summary written by the model, used only if pressure is still too high.

The idea is "lazy degradation": use the least disruptive fix first.

Recovery mechanisms

  • Retry with a higher output-token limit, up to 3 times.
  • Reactive compaction after a "prompt too long" error, once per turn.
  • Streaming fallback.
  • A fallback model.

Stop conditions: no tool use, maxTurns reached, context overflow, a hook stops it, or the user aborts.

Pattern: ReAct. It is reactive with no backtracking, trading search completeness for simplicity and latency.

5. Permissions and safety (Section 5)

Seven modes, from most to least supervised

ModeWhat it does
planYou approve the plan before anything executes.
defaultMost actions ask for approval.
acceptEditsAuto-approves edits and simple filesystem commands.
autoAn ML classifier decides.
dontAskAnything that would prompt is auto-denied.
bypassPermissionsSkips most prompts, but safety-critical checks still apply.
bubbleInternal only. A subagent escalates to the parent terminal.

Seven safety layers — any one of them can block an action

  1. Tool pre-filtering: denied tools are hidden from the model entirely.
  2. Deny-first rules: a broad deny beats a narrow allow.
  3. Mode constraints.
  4. The auto-mode classifier (yoloClassifier.ts): a fast filter, then chain-of-thought.
  5. Shell sandbox: filesystem and network isolation. Authorization and isolation are separate axes.
  6. Permissions are not restored on resume.
  7. Hooks: PreToolUse and PermissionRequest.

A key behavior: a denial is treated as a routing signal, not a hard stop. The model gets the reason and tries a safer approach.

Weaknesses the paper names

  • Commands with more than 50 subcommands fell back to a single generic prompt and skipped per-subcommand deny checks. Parsing them one by one froze the UI. Defense-in-depth fails when layers share failure modes, here performance.
  • Pre-trust initialization CVEs (CVE-2025-59536, CVE-2026-21852): MCP servers and settings environment variables ran before the user accepted the trust dialog. The pipeline has a spatial order of checks but missed the temporal question of when each check becomes active.
  • A sandbox hostname null-byte bypass, with no CVE assigned.
  • All of these were patched.

6. Extensibility (Section 6)

Why four mechanisms instead of one? Each costs a different amount of context.

MechanismUnique roleContext costWhere it plugs in
HooksLifecycle interception (27 events)Zero by defaultexecute()
SkillsDomain instructions (SKILL.md)Low until invokedassemble()
PluginsPackaging and distribution (10 component types)MediumAll three points
MCPExternal toolsHigh once schemas loadmodel() tool pool

Three injection points in any agent loop

  • assemble() controls what the model sees.
  • model() controls what it can reach.
  • execute() controls whether an action runs.

This framing is worth remembering.

Hooks in detail

  • 27 event types, of which 5 are safety-related.
  • 4 persisted command types: shell, LLM prompt, HTTP, and agent verifier.

Tool pool

  • Up to 54 built-in tools: 19 always present and 35 conditional.
  • Built-in tools win over MCP tools with the same name.
  • The pool is assembled the same way everywhere by assembleToolPool().

7. Context and memory (Section 7)

CLAUDE.md has four levels: managed (OS), user (~/.claude), project (checked into the repo), and local (gitignored).

  • Files closer to the working directory load later and get more attention.
  • Files in subdirectories load lazily, only when the agent reads files there.

A key insight: CLAUDE.md is sent as a user message, not as the system prompt. So the model follows it probabilistically. Permission rules are the deterministic enforcement. The design separates guidance from enforcement on purpose.

Memory retrieval

  • No embeddings and no vector database.
  • An LLM scans memory-file headers and picks up to 5 files.
  • The trade: transparency over retrieval precision.

Compaction

  • It only appends boundary and summary events. It never deletes lines from the transcript.
  • After compaction, plans, skills and running agents are re-announced, because compaction drops those attachment messages.

8. Subagents (Section 8)

Built-in types: Explore (read-only), Plan, general-purpose, Claude Code Guide, Verification, statusline-setup. Custom agents go in .claude/agents/*.md.

Isolation modes

  • In-process (the default): a separate conversation, but the same files.
  • Git worktree: a separate copy of the repo, with no containers needed.
  • Remote: internal only.

What comes back: only the summary text returns to the parent. The full history is saved in a separate "sidechain" .jsonl file. This matters because agent teams use about 7x the tokens of a normal session.

Permission precedence: if the parent is in bypass, acceptEdits or auto mode, that wins over the subagent's own mode, because it reflects an explicit user decision.

Agent teams coordinate through files: JSON inboxes with lockfiles, not a message broker. The trade is throughput for zero dependencies and easy debugging.

SkillTool vs. AgentTool: a skill injects instructions into the current context. An agent always gets a new, isolated context.

9. Persistence (Section 9)

Three separate channels:

  • Per-session JSONL transcripts.
  • Global history.jsonl, which holds only your prompts (it powers Up-arrow and Ctrl+R).
  • Subagent sidechain files.

Resume and fork replay the transcript but do not restore session permissions. This is deliberate: old trust decisions shouldn't carry into a context that may have changed.

Checkpoints are only file snapshots for --rewind-files. They are not a general state store.

Hermes safety detail: it has hard-coded blocked patterns (rm -rf /, mkfs, fork bombs) and 3 modes: manual, smart and off.

Lessons from the comparison

  • The questions stay the same across systems. The answers depend on how each system is deployed.
  • The systems compose rather than compete. OpenClaw can host Claude Code through ACP, and Hermes can be both host and guest.
  • So the design space is layered, not a flat list of alternatives.

11. Discussion: the most quotable parts (Section 12)

The harness matters as much as the model

  • Changing only the harness moves one model's score by up to 18 points on long-horizon tasks.
  • The harness alone moves Fable 5's pass rates by 10+ points.

Does a stronger model need less harness? Only the decision scaffolding (planning and control logic) shrinks.

  • Safety, human authority and adaptability don't depend on how capable the model is.
  • Context is still finite, and tokens still cost money.
  • A stronger model is riskier, not safer.

Value tensions

  • Authority vs. safety: approval fatigue.
  • Safety vs. capability: the 50-subcommand fallback.
  • Adaptability vs. safety: MCP attack surface and the CVEs.
  • Proactivity vs. disruption: 12–18% more tasks done, but users dislike frequent interruptions.
  • Velocity vs. coherence.

Evidence on long-term costs (studies on adjacent tools, not Claude Code itself)

  • Developers were 19% slower while believing they were 20% faster (an RCT with 16 developers).
  • Cursor adoption led to +40.7% code complexity, and the speed boost faded by month 3.
  • In 304K AI-written commits, about 25% of the issues introduced persisted, and security issues persisted more.
  • An EEG study found weaker neural connectivity in LLM users.
  • Entry-level tech hiring fell 25%.

The paper's prediction: the agent's limited view of the codebase plus isolated subagents will cause duplicated code and convention violations. Good local decisions can still produce poor global results.

A Claude Code-specific finding: cleaner code didn't change pass rates, but it cut tokens by 7–8% and file revisits by 34%.

Other limitations the paper flags

  • Compaction is mostly invisible to the user.
  • The four extension mechanisms interact in ways that are hard to predict.
  • Feature flags mean different builds behave differently.

KAIROS: a feature-flagged proactive background agent. It wakes on <tick> prompts, notices whether you're at the terminal, and uses a SleepTool for cost control (the prompt cache expires after 5 minutes). It's unconfirmed whether it's active in production.

Three recurring design choices

  1. Graduated layers instead of single mechanisms.
  2. Append-only storage: auditability over query power.
  3. Model judgment inside a deterministic harness.

12. Six open questions (Section 13)

  1. Silent failures and the observability/evaluation gap:
    • About 78% of AI failures are invisible.
    • 89% of teams have observability, but only 52% run offline evaluation.
    • Should the harness itself contain an evaluator?
  2. Cross-session persistence:
    • What belongs between static CLAUDE.md and a single session's transcript?
    • The paper mentions Claude Code's Projects beta as one step here.
  3. The harness boundary: where it runs (managed or virtualized agents), when it acts (proactive), what it acts on (robots and the physical world), and with whom (multiple agents).
  4. Horizon scaling: from single sessions to work that spans weeks.
    • The paper says v2.1.154 added dynamic workflows: the model writes a JavaScript orchestration script that can fan out to up to 1,000 subagents, with intermediate results kept outside the model's context.
  5. Governance:
    • EU rules (the GPAI Code of Practice).
    • Only 13.3% of agent systems publish safety cards.
    • The paper says a June 2026 US export-control order briefly pulled Fable 5 and Mythos 5 offline.
  6. Long-term developer capability: can the system measure and protect human understanding? Right now the harness has no per-session signal for it.

Conclusion: the most important open question is not how to add more autonomy. It's how to preserve human capability over time, and the paper argues this should be a first-class design problem.

How to be "better than the person who read it all"

Be critical, not only informed

  • The analysis is a single snapshot (v2.1.88) of code that leaked through npm. Feature flags mean you can't tell what is actually enabled in production.
  • The "1.6% decision logic" figure is Tier C: community-estimated, not verified.
  • The long-term-harm evidence comes from Cursor, Copilot and other tools, not Claude Code. The authors admit this.
  • The defense-in-depth argument assumes the layers fail independently. The paper's own CVE and 50-subcommand examples show they don't.

Useful lessons for your own coding agent

  • Keep the loop dumb and the harness smart.
  • Make denials feedback to the model, not crashes.
  • Run cheap context reduction before expensive summarization.
  • Have subagents return summaries, not full transcripts.
  • Separate soft guidance (prompt files) from hard enforcement (code rules).
  • Never let anything run before the user has accepted trust.
